## What the sources state

### (a) Delegation is selective, not the default: Anthropic

**\`https://www.anthropic.com/engineering/building-effective-agents\`** (Anthropic engineering blog, fetched 2026-09-26; author names not shown in the fetched fragment). States directly:

- "In the orchestrator-workers workflow, a central LLM dynamically breaks down tasks, delegates them to worker LLMs, and synthesizes their results."
- When to use: "complex tasks where you can't predict the subtasks needed (in coding ... the number of files that need to be changed and the nature of the change in each file likely depend on the task)". "the key difference from parallelization is its flexibility - subtasks aren't pre-defined, but determined by the orchestrator based on the specific input."
- On voting/parallel review: "Voting: Reviewing a piece of code for vulnerabilities, where several different prompts review and flag the code if they find a problem." "For complex tasks with multiple considerations, LLMs generally perform better when each consideration is handled by a separate LLM call, allowing focused attention on each specific aspect." (Note: this is the *positive* claim for voting; the project's own finding - correlated agents buy correlated error - is not addressed here.)

**\`https://www.anthropic.com/engineering/multi-agent-research-system\`** (Anthropic engineering blog, fetched 2026-09-26) is the strongest *published* evidence on both sides:

- Help: "a multi-agent system with Claude Opus 4 as the lead agent and Claude Sonnet 4 subagents outperformed single-agent Claude Opus 4 by **90.2%** on our internal research eval" (breadth-first search tasks).
- Mechanism: "token usage by itself explains 80% of the variance" of BrowseComp performance; "Multi-agent systems work mainly because they help spend enough tokens to solve the problem"; "The essence of search is compression ... Subagents facilitate compression by operating in parallel with their own context windows ... before condensing the most important tokens for the lead research agent."
- Hurt / cost: "agents typically use about **4x** more tokens than chat interactions, and multi-agent systems use about **15x** more tokens than chats ... multi-agent systems require tasks where the value of the task is high enough to pay for the increased performance."
- **When not to use**: "some domains that require all agents to share the same context or involve many dependencies between agents are not a good fit for multi-agent systems today. For instance, most coding tasks involve fewer truly parallelizable tasks than research, and **LLM agents are not yet great at coordinating and delegating to other agents in real time.**"

### (b) The negative result: Cognition

**\`https://cognition.com/blog/dont-build-multi-agents\`** - "Don't Build Multi-Agents", Walden Yan, **06.12.25** (date and author shown on page; fetched 2026-09-26). Two named principles: **"Share context"** and **"Actions carry implicit decisions."** Verbatim, the load-bearing claims:

- The split-task pattern is "**very fragile**"; the Flappy-Bird example: subagent 1 builds a Super Mario background, subagent 2 builds a bird that "moves nothing like the one in Flappy Bird", and "the final agent is left with the undesirable task of combining these two miscommunications."
- "I would argue that Principles 1 & 2 are so critical, and so rarely worth violating, that you should **by default rule out any agent architectures that don't abide by them**."
- Recommended default: "the simplest way to follow the principles is to just use a **single-threaded linear agent**", with an optional dedicated **compression** model that "compress[es] a history of actions & conversation into key details, events, and decisions" (they "fine-tun[ed] a smaller model" for this).
- "running multiple agents in collaboration only results in fragile systems. The decision-making ends up being too dispersed and context isn't able to be shared thoroughly enough."
- On Claude Code specifically (as of June 2025): "it never does work in parallel with the subtask agent, and the subtask agent is usually only tasked with **answering a question, not writing any code**. Why? The subtask agent lacks context from the main agent that would otherwise be needed to do anything beyond answering a well-defined question."

### (c) A taxonomy with measured failures, not a demo: MAST

**\`https://arxiv.org/abs/2503.13657\`** - "Why Do Multi-Agent LLM Systems Fail?", Cemri, Pan, Yang, Agrawal, Chopra, Tiwari, Keutzer, Parameswaran, Klein, Ramchandran, Zaharia, Gonzalez, Stoica; submitted 17 Mar 2025, revised v3 26 Oct 2025. Verbatim:

- "Despite enthusiasm for Multi-Agent LLM Systems (MAS), **their performance gains on popular benchmarks are often minimal.**"
- MAST-Data: "1600+ annotated traces collected across 7 popular MAS frameworks"; the taxonomy was built from "rigorous analysis of 150 traces" with "high inter-annotator agreement (**kappa = 0.88**)", yielding "**14 unique modes**, clustered into 3 categories: (i) system design issues, (ii) inter-agent misalignment, and (iii) task verification." (Category (iii) is the harness-relevant one: "task verification" - *the orchestrator cannot verify what it did not do*.)
- Analyzed across "GPT4, Claude 3, Qwen2.5, CodeLlama" and "coding, math, general agent" tasks.

This is the paper to cite when the question is "does delegation pay for itself". It does not give a single effect size for "subagent vs no subagent"; it gives a failure distribution. (Secondary, unfetched: the paper argues failures need "more sophisticated solutions".)

### (d) Vendor docs: what the vendors say their harnesses do

**Claude Code** - \`https://code.claude.com/docs/en/sub-agents.md\` (fetched 2026-09-26; no publication date shown). This is **first-party product documentation**, i.e. authoritative about intent but not independently verified:

- Purpose list: "**Preserve context** ... **Enforce constraints** by limiting which tools a subagent can use ... **Specialize behavior** ... **Control costs** by routing tasks to faster, cheaper models".
- Definition carries: \`name\`, \`description\`, \`tools\`, \`model\`, \`permissionMode\`, \`mcpServers\`, \`skills\`, \`hooks\`, \`isolation: worktree\`, \`omitClaudeMd\` (frontmatter; the doc's "Available tools", "Permission modes", "Enable persistent memory", "Supported frontmatter fields" sections). Body = the system prompt.
- Delegation signal: "Claude uses each subagent's \`description\` to decide when to delegate tasks"; combined non-built-in descriptions are warned at **15,000 tokens** - so *descriptions are context*, paid on every parent turn.
- **Enforcement is host-side, documented as a filter chain**, not a prompt request: "the first removes a short list of tools from every subagent, and the second reduces the built-in tool set for subagents that run in the background ... The first filter removes these tools, **even when listed in the \`tools\` field**"; and "Claude Code removes every other built-in tool from a background subagent, **whether inherited or listed in the \`tools\` field**, so the same definition can resolve to different tools in the foreground and the background." Built-ins: Explore and Plan are "read-only tools; **Write and Edit are denied**".
- Concurrency: "By default, when **20 subagents** are running in a session, spawning another with the Agent tool fails with \`Concurrent subagent limit reached\`" (env \`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS\`); nesting depth default **3** (\`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH\`); "At the depth limit, Claude Code **withholds the \`Agent\` tool** from every subagent".
- Context isolation: "Each subagent starts with a **fresh, isolated context window**. It doesn't see your conversation history, the skills you've already invoked, or the files Claude has already read. Claude composes a delegation message that summarizes the task." Loaded at startup: its own system prompt, the delegation message, the CLAUDE.md hierarchy, a git-status snapshot, preloaded skills, a sibling roster. A "fork" is the exception and inherits the conversation.
- Explicit "**when not to**" section ("Choose between subagents and main conversation"): use the main conversation when "the task needs frequent back-and-forth or iterative refinement", "multiple phases share significant context, such as planning, implementation, and testing", or "latency matters. A subagent that isn't a fork starts fresh and may need time to gather context". Also: "For a question about something already in your conversation, use \`/btw\` instead of a subagent."

**OpenAI Agents SDK** - \`https://openai.github.io/openai-agents-python/handoffs/\` and \`/tools/\` (fetched 2026-09-26). "Handoffs are represented as tools to the LLM. So if there's a handoff to an agent named Refund Agent, the tool would be named \`transfer_to_refund_agent\`." Handoff options: \`tool_name_override\`, \`tool_description_override\`, \`on_handoff\`, \`input_type\`, \`input_filter\`, \`is_enabled\`, \`nest_handoff_history\`.

**agency-swarm docs** - \`https://agency-swarm.ai/core-framework/agencies/communication-flows.md\` (fetched 2026-09-26), first-party. Contains an unusually explicit comparison table:

| Pattern | Reliability | Autonomy | Costs | When to use |
|---|---|---|---|---|
| Handoff | **Very High** | Low | Lower | "Sequential workflows where each step requires tight feedback from the user" |
| Orchestrator-Worker | **Lower (mitigated with guardrails)** | Very High | Higher | "Complex multi-step tasks with independent not-very-high stakes steps" |

and a blunt warning: "**Always start with one agent.** Never build two agents simultaneously unless you know exactly what you're doing. The more agents you have, the harder it becomes to train them on specific tasks." The orchestrator pattern is described as "Agents use other agents as specialized tools through the \`SendMessage\` mechanism. Control always returns to the orchestrator after each delegation."

**CrewAI** - role/goal/backstory model is documented at \`docs.crewai.com\` (DNS not resolvable from this session; **not fetched**) - treated below from code only.

**OpenHands** - \`https://docs.openhands.dev/usage/prompting/microagents-overview\` (fetched 2026-09-26; page now titled "Skills Overview"; \`docs.all-hands.dev\` 301s here). Microagents have become **Skills** (Agent Skills spec) with OpenHands extensions "keyword triggers and path-triggered rules". The decisive sentence for this project: "**Skills guide the agent's behavior; they do not grant permissions or install dependencies by themselves. The agent can only use the files, tools, secrets, and network access available in its environment.**" I.e. in OpenHands a microagent is *context injection*, not a capability grant.

### 2. What an agent definition carries

- **Google ADK** (\`src/google/adk/agents/llm_agent.py\`): \`LlmAgent\` fields include \`mode: Literal['chat','task','single_turn']\` ("The delegation mode for this agent ... chat: Standard chat agent reachable via transfer_to_agent. task: Task agent ... single_turn: Agents that complete a task without chatting with the user."); \`parallel_worker: bool\`; \`disallow_transfer_to_parent\` / \`disallow_transfer_to_peers\`; **\`include_contents: Literal['default','none']\`** where \`'none'\` means "Model receives no prior history, operates solely on current instruction and input"; and \`input_schema\` documented as "The input schema when agent is used as a tool" plus \`output_schema\`. So ADK encodes **delegation mode, history policy and the tool-call contract in the definition**.
- **agency-swarm** (\`src/agency_swarm/agency/core.py\`): \`Agency(*entry_point_agents, communication_flows=None, name=None, shared_instructions=None, shared_tools=None, shared_tools_folder=None, shared_files_folder=None, shared_mcp_servers=None, send_message_tool_class=None, load_threads_callback=None, save_threads_callback=None, user_context=None, ...)\`. Note \`shared_instructions\` / \`shared_tools\` / \`shared_mcp_servers\`: the *agency* can hold context and tools common to all agents - a shared-context design, opposite to Claude Code's fresh-window default.
- **CrewAI** (\`lib/crewai/src/crewai/agent/core.py\`): \`role\`, \`goal\`, \`backstory\`, \`tools\`, \`allow_delegation\`, \`max_iter\`, \`max_rpm\`, \`llm\`, \`knowledge_sources\`, \`mcps\`, \`apps\`, \`step_callback\`. \`allow_delegation\` is documented as "Whether the agent is allowed to delegate tasks to other agents" and controls whether the delegation tools are attached at all.
- **LangGraph supervisor**: the definition is a compiled graph + a \`create_supervisor(...)\` call; the child is "a LangGraph \`CompiledStateGraph\`, a functional API workflow, or any other \`Pregel\` object". \`output_mode\` is \`'full_history' | 'last_message'\` with \`'last_message'\` the default - i.e. **the parent state gets only the child's last message by default**, and \`add_handoff_messages\` / \`add_handoff_back_messages\` control the transcript bookkeeping.

### 3. Context isolation, in code

- **Claude Code**: fresh window; parent passes a synthesised delegation message; child returns a summary; the exception is \`fork\` (inherits the conversation). (docs, not code.)
- **Google ADK**: \`include_contents: 'none'\` on a subagent is the switch that makes the child "operate solely on current instruction and input" - a per-agent, declared context policy (\`llm_agent.py\`).
- **LangGraph supervisor**: \`output_mode='last_message'\` (default) compresses the child's output; \`full_history\` does not. There is a companion extension in the ecosystem ("Tool output trimmer" appears in the OpenAI Agents SDK docs nav; LangChain has message trimming) but I did not read those sources.
- **agency-swarm**: the opposite default - a **shared thread**; \`shared_instructions\` and \`load_threads_callback\`/\`save_threads_callback\` are about persisting one conversation across agents rather than isolating children.
- **OpenHands**: "progressive disclosure" of skills (per the docs nav) - skills are loaded on trigger, which is a *context* mechanism.

### 4. Concurrency, in code and docs

- **LangGraph supervisor** (\`supervisor.py\`): \`create_supervisor(..., parallel_tool_calls: bool = False, ...)\` - **parallel tool calls are off by default**; there is \`_supports_disable_parallel_tool_calls\` with \`MODELS_NO_PARALLEL_TOOL_CALLS = {"o3-mini","o3","o4-mini"}\`. \`handoff.py\` contains \`_remove_non_handoff_tool_calls(...)\`, commented "if the supervisor is calling multiple agents/tools in parallel, we need to remove tool calls that are not meant for this agent **to ensure that the resulting message history is valid**" - i.e. parallel handoffs corrupt shared history and are repaired by deleting the siblings' calls.
- **Claude Code** (docs): hard cap of 20 concurrently running subagents; depth cap 3; \`isolation: worktree\` gives a subagent "an isolated copy of the repository" and Bash/PowerShell run inside the worktree; a command resolving into the main checkout "fails with an error" (v2.1.203+). This is the **only per-file conflict mechanism I found implemented anywhere**: give the child a different checkout.
- **Google ADK**: \`parallel_worker: bool\` on \`LlmAgent\` (field present; semantics not read further).
- No project I read implements **file-level leases / effect de-duplication across siblings**. CrewAI's shared \`tools_handler\` and \`_times_executed\` counter are per-agent, not a global effect ledger.

### 5. The local repository already has the shape of an answer (and it is unwired)

- \`src/core/subagent.ts\` defines \`SubagentRequest { dispatchId, name, prompt, cwd, capabilities: readonly SubagentCapability[], provider? }\` with \`SubagentCapability = "read" | "grep" | "find" | "ls"\`, plus a \`SubagentProvider\` interface (\`inspect/launch/collect/cancel\`) and a \`SubagentTerminal { state, value, error, usage }\`. The capabilities list is **in the request object, not in the prompt** - which is the right shape.
- \`src/core/dispatch-policy.ts\` - \`decideDispatch(estimate, hasLongRunningIsolation)\` is an explicit, testable delegation policy: \`inline\` if \`estimate.hasSharedMutableState || predictedWallTimeMs < 60_000\` ("coupled or short work stays inline"); \`subagent\` for isolated >120s work; \`parallel\` for \`independentBranches >= 2\` and >60s ("independent branches have a join point"); \`subagent\` when \`dispatchCost <= inlineCost * 0.8\` or \`predictedWallTimeMs * 0.75 < inlineCost\`; else \`inline\` because "coordination overhead does not justify dispatch".
- \`src/core/capability-scope.ts\` - \`narrow(parentAgentId, child)\` "**a delegate may narrow its authority, never widen it**"; capability set "stored outside the model's context"; resource language deliberately not full globs because "a guess in this direction is a privilege escalation". This is the enforcement primitive a subagent contract should be built on.
- \`src/core/context-admission.ts\` - compacts oversized tool results into \`{ digest, artifactRef, head, omittedCharacters }` so "the raw payload never appears in model-visible content"; guards three channels (\`tool_result\`, \`extension_message\`, \`background_notification\`) because a compaction bypass was recorded in this repo's history (a 2,865,326-char payload). This is exactly the "compress the child's answer" component, and it already exists.
- \`.trellis/agents/implement.md\` and \`check.md\`: frontmatter is only \`name/description/provider/labels\` - **no tool list**. In the same \`.trellis/agents/*.md\` bodies, \`## Forbidden Operations\` says \`git commit\` / \`git push\` / \`git merge\` are forbidden. That is a **request**.
- \`.codex/agents/trellis-implement.toml\` etc.: \`sandbox_mode = "workspace-write"\` (host-enforced), and a **recursion guard written as prompt text** ("You MUST NOT spawn another \`trellis-implement\` ... Only the main session is allowed to dispatch"). The recursion guard is prose; nothing in the definition is a machine-checkable depth limit.
- Net: this repository already separates the two surfaces (prompt-level rules in \`.md\`; host-level sandbox in \`.toml\`) and already holds \`src/core\` contracts for capability narrowing, dispatch policy, and result compression. The gap is that nothing loads them (per the task's own PRD).

## What is transferable to a harness

**(i) The smallest useful subagent contract.** Every design I read that *enforces* rather than *requests* needs the same five things; anything else is selection metadata:

1. **Identity + selection text** (\`name\`, \`description\`) - read by the parent to *choose*, and paid for in the parent's context on every turn (Claude Code warns at 15k combined tokens). Keep it short.
2. **Capability set, held outside the model's context** - a typed list (\`read\`/\`write\`/\`exec\`/\`net\`/effect verb) with optional resource scope and expiry. Enforced by the dispatcher (ADK's \`TransferToAgentTool(agent_names=...)\`, LangGraph's \`ToolNode\`, agency-swarm's per-pair \`SendMessage\`, this repo's \`capability-scope.ts\`). *A restriction that lives in the prompt is not a restriction.*
3. **Delegation edges** - who may be invoked by whom, and in which direction (agency-swarm \`communication_flows\`; ADK \`disallow_transfer_to_*`; LangGraph \`agent_names\`). Default closed; a delegate may **narrow** but not widen.
4. **Context policy** - inherit nothing vs. inherit history (ADK \`include_contents\`; Claude Code fresh vs. fork), plus a **bounded output contract** for what returns (schema + size cap + artifact reference - this repo's \`context-admission.ts\` already does it).
5. **Execution envelope** - model/provider, wall-time/token budget, isolation mode (worktree/sandbox), max depth, max concurrent children.

Missing from almost everyone: a **verification handle** on what the child did. The child's summary is the parent's only evidence, and MAST's third failure category is exactly "task verification". A harness that can enforce should return, alongside the summary, the *effect/evidence references* (files touched, commands run, diff digest) so the parent can check without re-doing. That is the transferable lesson, not a feature of any of these projects.

**(ii) Delegation is a policy with thresholds, and the thresholds are written down.** This repo's \`dispatch-policy.ts\` (coupling and wall-time floors, cost-ratio threshold, "coordination overhead does not justify dispatch") is a better artefact than any of the external projects, which mostly delegate by model judgment (Claude Code: "Claude uses each subagent's \`description\` to decide"). Keep the policy testable and default to inline.

**(iii) Put the negative cases in the policy, citing the sources.** Independent, breadth-first, verbose, self-contained work → delegate (Anthropic's 90.2% is on a *research/breadth* eval; note it is an internal eval and is also explained by 15x token spend). Shared mutable state, coupled phases, work needing the user in the loop, or latency-sensitive work → inline (Anthropic's own "not a good fit ... most coding tasks"; Cognition's "fragile"; this repo's \`hasSharedMutableState → inline\`).

**(iv) Concurrency: the only sound mechanisms found are isolation and caps.** Concrete options, in order of strength: per-child **worktree/sandbox** (Claude Code \`isolation: worktree\`); **serialise** the risky channel (LangGraph \`parallel_tool_calls=False\` and its sibling-call stripping); **cap** concurrency and depth (Claude Code 20 / depth 3); and, above all, a **single-writer effect ledger** - none of the projects have one, this repo's \`effect-ledger.ts\` does, and that is the piece to wire rather than reimplement.

**(v) Do not build a third layer.** The harness needs the \`.trellis/\` prompt/assets surface *and* the \`src/core\` enforcement surface, each in exactly one place: agent prose in \`.trellis/agents\` (or wherever Trellis now resolves them), and the capability/dispatch/compression contracts in \`src/core\` made load-bearing by the Pi host. Two implementations of one contract is this project's documented failure mode.

# A1 设计：自有 loop 的最窄端到端路径（同仓）

## 边界

**在本仓内工作**（形状决定：产品与运行时同一个仓）。不新开仓、不迁移、**不动宿主（Pi）的 loop**。

## 决策 1：入口放 CLI，不放测试专用路径

| 方案 | 取舍 |
|---|---|
| 只在 `tests/` 里驱动 | 代价最小，但**可达性走查不认它**（四个 `harness-*.mts` 就是先例：登记理由写着"consumed by `scripts/…` and its test; **deliberately not reached by the harness**"）→ allow-list 条目永远删不掉，等于把"提升为生产"降级成"测试能跑" |
| **`src/cli.ts` 加诊断子命令（选定）** | 它是产品入口（`bin/` 指向它），走查会跟着；它不碰宿主正在用的 loop；诊断本来就是它的职责 |
| 在 `runtime.ts` 里组合并让宿主改用 | 那是 **loop 拥有权**那一格（S6 量级），本任务不做 |

## 决策 2：闸门在 loop 内，入口只负责组装

`createAgentLoop` 的 `LoopOptions` 已经接受 gate，所以**不新增开关**。判定与补救沿用 `action-policy` 的既有形态。

## 决策 3：keep / revert 在**临时仓**里演练

理由：本仓历史是记录，不该被测试提交污染。做法：`mkdtemp` + `git init` + 一次真实提交（keep，记 hash）→ `git revert`（记 hash）；两处写进账本与读数。

## 决策 4：组件挂载点

七个组件各一个**固定文件位置**、且**可被程序化修改**（语料硬要求：*"General extensibility alone is insufficient."*）。本任务只把它们**指出来**（文件级），不实现新能力。

## 提交与回退形态

**一次逻辑改动 = 一次提交**；`git revert` 是唯一回退路径（不引入第二套机制）；必须能干净回退**两次连续**的改动。

## "门禁不下降"的定义（取代原 AC-4 的"跨仓等价"）

不是"跑得起来"，而是**同一套测试、同一棵树，三条读数不降**：`typecheck` 0 · `test` 822/820/0/2 · installer 141。差异必须逐条解释，不能笼统声明。

## 风险

- **把"提升"做成"重写"**：`loop-runner`、`loop-scripted` 已存在且被测试钉着 → 只许接线；任何改动单独提交。
- **入口不构成"生产可达"**（走查不跟 CLI 这条路径）→ 第 1 步就**让它自己告诉我们**：先删条目跑走查，红就改入口，绿再继续。
- **临时仓的 Windows 细节**（行尾、文件模式）→ 演练只断言"提交与 revert 各一次、hash 可读"，**不断言行尾**。

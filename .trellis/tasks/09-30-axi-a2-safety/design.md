# A2 设计：五部件的数据流、状态载体与补救形态

## 边界

本任务实现 §2.2 的五个部件，并保证**每条检测器配一条确定性补救**。它是 axi 的验收核心，也是两块**无先例**之一。

## 决策 1：语法感知怎么做 → **第一版用命令解析 + 显式 arity/子命令表**，tree-sitter 留作后续替换

语料里 OpenCode 的做法是 tree-sitter + **约 130 条 arity 字典**——**字典本身才是主要工作量**，解析器是可以后换的实现细节。所以第一版把力气放在**表**上，解析器先用"分词 + 子命令识别"。

## 决策 2：跨调用状态的载体 → **loop 状态（session-scoped），不是消息历史**

理由是 §1.3 的攻击手法：*"retry until relevant context leaves the monitor's history"*。**只要状态活在上下文里，攻击就能等它被淘汰。** 所以：

- 状态落在 **loop 的会话状态**里，与消息历史分离；
- 压缩/淘汰**不得**影响它；
- 判定**不依赖"历史上出现过什么"**，只依赖状态机当前值 + 本次调用的语法结构。

## 数据流

```
调用意图
  → ① 语法解析（子命令 / 参数类别 / arity）
  → ② 策略判定（声明式规则 + 当前状态）
  → ③ 保持性传感器（这条声明是否仍在管住这一轮）
  → ④ pass ──► ⑤ 隔离层执行 ──► 事件（交给 A3 记录）
     remediate ──► 确定性重组 ──► ⑤
     refuse ──► 兜底（补救也做不出合法产物时）
```

## 决策 3：补救的形态 → **确定性的合法降级产物**，而不是拒绝

§1.1.1 的机制：外挂层输在"拦住了就没有补救"。所以每条检测器**必须**声明一个 `remediate` 分支，形态例如：退回模板、重新规划一次、丢弃违规片段后重组。

**兜底规则**：补救也不成功 → 才 refuse；且 refuse 必须**仍让回合结束**（A2 的 AC-4 看住这一点）。

## 决策 4：检测器与"两臂"的关系 → 检测器单一定义处，**分叉点只在补救**

照参考实现（`detectors.mjs` 是 single source of truth，`guardrail.mjs` 与 harness 共用它）。axi 保留这个结构，因为它让"代码内 vs 外挂"的差别**可测量地隔离在补救这一处**——将来若要复现 88/120 vs 120/120 的对照，只有这一个变量。

## 保持性传感器的定义（第五部件）

问的是"**这条声明是否仍然管住了这一轮运行**"，不是"是否存在"。落地：**每条声明登记一个消费端**；回合结束时检查消费端**被调用过**。没被调用 = 声明已成装饰 = 报警。

这是本仓"声明没有消费者"这个老毛病在安全文献里的正式名字（SAHOO 的 constraint-preservation check）。

## 与其余阶段的接口

- **给 A3**：本阶段产生**违规事件**，由 A3 的外部通道记录；**违规信号不由本阶段自报**（SSM 的教训）。
- **依赖 A0.2**：隔离那一格能否落实取决于 Job Objects 的结果；做不到就明确写下"我们不做 OS 隔离"。

## 风险

- **表覆盖不足**：arity 字典永远不全 → 用**故障注入**（AC-3）度量覆盖，而不是声称覆盖。
- **状态泄漏**：状态若进了上下文，攻击即可规避 → 用"重试到历史淘汰"那条测试看住。
- **补救本身违规**：确定性重组也可能产出违规内容 → 补救产物**必须再走一次检测**。

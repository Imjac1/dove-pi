## A0.1 DSH 隔离可用性（**需要用户执行**）

**假设**：在 `workspace-write` 会话里，越界写会被拒绝或升级为审批。

**为什么它是 Plane B 的前提**：Plane B 要求"存在一个改进者写不到的地方"。如果越界写**静默生效**，那么"判分权威外置"就只是文件布局上的说法，不是强制。

**方法**：在 `workspace-write` 会话中对 workspace 之外的一个已知路径执行一次写操作；同时在 workspace 内做一次写作为**对照**。然后检查三条判据。

**判据（三条全过才叫过）**
1. 越界写**不得静默生效**——**拒绝或升级为审批都算过**（弹窗不算失败）；
2. 界内写**静默成功**，且**删得掉**；
3. **被拒之后，回合仍能完成**（不得把循环打死）。

**配置注记**：`workspace-write` 预设带 `approval: ask`；无人值守形态需要 `sandbox: workspace-write` + `approval: never`，而**出厂预设没有这个组合**——若要用无人值守形态，需自加一条命名预设（属配置，不是产品代码）。

**若失败**：Plane B 不成立 → 方案退回"**人以纪律充当不动点**"，并且**照记读数**（这条退路必须被写下来，而不是悄悄消失）。

## A0.2 Windows 隔离原语（Job Objects / restricted tokens）

**假设**：可以用 Job Objects（必要时叠加 restricted token）做出"一个目录树对某受约束进程不可写"。

**为什么必须自己测**：这是 axi 在 Windows 上唯一靠谱的 **OS 级**答案，也是唯一必须二开的**系统级**部件；语料对 Omnigent 的记录（bubblewrap+seccomp / Seatbelt / **Job Objects**）说明这一层本来就"抗拒被抽成共享服务"。

⚠️ **设计期间已修正的措辞**（A0.2 第一半的读数，见 `readings.md`）：**Job Objects 本身不限制文件系统写**。文件系统那一半来自 **ACL + 安全令牌**，Job Object 的角色是**绑定进程集合并施加令牌**。所以本实验测的是**两者配合**，而不是"Job Object 做到了隔离"——避免把机制说成它没做的事。

**方法**：写一个最小宿主进程，在 Job Object 下启动子进程，让子进程尝试写目标树；同时让它在目标树**之外**完成一件正常事务（证明没被"打死"）。

**判据**
1. 受约束进程**确实写不进**目标树；
2. 它**仍能正常完成一个回合**。

**若失败**：明确选"策略 + 内容侧防御"这条路线，并**写下"我们没有 OS 隔离"**——可接受，但**不可声明**成有。

## A0.2 后半（下一步）：受限令牌 + ACL

**为什么不是 Job Objects**：`readings.md` A0.2 已把机制说清——**Job Objects 本身不限制文件系统写**；它的角色是绑定进程集合并**施加安全令牌**（`JOBOBJECT_SECURITY_LIMIT_INFORMATION` 需要 `SeTcb`，本机令牌没有，这一条预期不可用，但**要用实测取码，不从特权清单推断**）。文件系统那一半必须由 **ACL + 受限令牌**给。

**假设**：以**当前进程主令牌的受限版本**（`CreateRestrictedToken` + 限制 SID 列表）起的子进程，
1. **写不进**目标树（Plane B 的替身）；
2. **摘不掉**那条限制——这正是与 A0.2 结论 2 的差别：**不是**"同一身份可以把自己打的 deny 摘掉"；
3. **仍能在目标树之外完成一件正常事务**（不得把进程打死）。

**机制形状（不当作已验证的 API 顺序；每一步都读回实际值）**：由 axi 拥有的那个小进程（jailer）先给**目标树**设好 ACL，再以受限令牌起改进者；改进者的可写面只到"jail 树"，目标树对它**没有授予**（必要时显式 deny）。

**三个必须实测、不许推断的未知**（每一个都能单独否掉结论）：

1. **受限 SID 列表究竟能不能建立**：`CreateRestrictedToken(..., SidsToRestrict)` 之后用 `GetTokenInformation(TokenRestrictedSids)` **读回**实际列表；**列表为空 = 机制没生效，不是"拦住了"**。这是本实验的仪器自检。
2. **属主隐含的 DACL 写权限会不会绕过限制**：文件属主对 DACL 有隐含的写权限，所以"摘不掉"必须真的测；若被绕过，退路是显式 deny ACE（含 `OWNER RIGHTS`，`S-1-3-4`），或让目标树的属主不是被约束的身份。
3. **受限进程还能不能跑起来**：限制 SID 同时会挡住系统 DLL 的加载（那些授予通常给 `Everyone` / `Users`，不给我们的限制 SID）→ "进程根本没起来"与"被挡住了"必须区分开，**每次都要有基线对照**（同一条写操作先以无限制身份成功一次）。

**判据（三条全过才叫过）**

1. 受限进程对目标树写**失败**，且**不是**因为进程没起来（有基线对照 + 可观测的尝试日志）；
2. 受限进程**无法**移除目标树上的限制（移除后再试写，仍失败）；
3. 受限进程在 jail 树里（目标树之外）**能完成一件正常事务**（写一个文件并读回）。

**若失败**：写出"**我们没有 OS 隔离**"，A2 明确改走"策略 + 内容侧防御"，Plane B 退回"人以纪律充当不动点"。**这是有效结论，照记。**

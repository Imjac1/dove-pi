# Research: Harness entry gates and AI conventions

- **Query:** Part A - where does an agent harness check an action *before* it happens, what happens when the check cannot be made, and what published evidence exists of gates being bypassed. Part B - how a repository tells an agent how to behave in it, and whether anything *checks* the agent against those conventions.

Conventions: AGENTS.md, CLAUDE.md, Cursor `.mdc`, Copilot instructions, Kiro steering, spec-driven development, Zed (not reachable). For a base agent harness that must be vertical-agnostic, load-bearing, and single-implementation.

## What the sources state

### Part A - the entry gate

**Claude Code.**
**[SOURCE]** Hooks fire "on every tool call inside the agentic loop: `PreToolUse` and `PostToolUse`, **except `EndConversation` calls, which skip both**". `PreToolUse` can return `permissionDecision` of `allow | deny | ask | defer`; "Deny and ask rules are still evaluated regardless of what the hook returns". "Exit 2's block is the one outcome JSON can't override." "Deny rules block in every mode, including `bypassPermissions`. Deny and ask rules don't apply to `EndConversation` as long as Claude still has at least one other tool it can call. Allow rules have no effect in `bypassPermissions`." There is a documented "Actions no mode auto-approves" set.
**[SOURCE] What happens when the gate cannot evaluate:**
- "A timed-out `command`, `http`, or `mcp_tool` hook **doesn't block the tool call**. The call continues through the normal permission flow, so **don't count on a stalled hook to act as a gate**." An Agent SDK *callback* hook that exceeds its timeout **does** block.
- "a parsed object that **fails schema validation** is a **non-blocking error: the action proceeds**" (same for unparseable stdout, on any exit code other than 2).
- `PermissionRequest` hook: exit code 2 "isn't honored for this event".
- `SessionStart` and `Setup` fire before MCP servers are available, so `mcp_tool` hooks on them are skipped.

**Codex.**
**[CODE]** `AskForApproval`: `UnlessTrusted` ("Commands require approval unless an explicit exec policy rule allows them"), `OnRequest` (model decides when to ask; default; `on-failure` is a serde alias), `Granular(GranularApprovalConfig)`, `Never` ("Failures are immediately returned to the model, and never escalated to the user for approval"). `GranularApprovalConfig` is explicitly fail-closed: "When a field is `true`, commands in that category are allowed. When it is `false`, **those requests are automatically rejected instead of shown to the user**."
**[CODE]** The sandbox is now a declarative filesystem policy, not just a mode string: `FileSystemSandboxKind{Restricted|Unrestricted|ExternalSandbox}`, `FileSystemAccessMode{Read|Write|Deny}` with **"conflict precedence rather than capability breadth: `deny` beats `write`, and `write` beats `read`"**, plus `NetworkSandboxPolicy{Restricted|Enabled}`. `codex-rs/core/src/safety.rs` returns `SafetyCheck{AutoApprove|AskUser|Reject}` and carries reasons `"writing outside of the project; rejected by user approval settings"` and `"writing is blocked by read-only sandbox"`. Observed but not investigated: `GuardianAssessmentOutcome`, `GuardianRiskLevel`, `GuardianUserAuthorization` re-exported from `protocol.rs`, i.e. Codex has a risk-assessment/auto-review component with the same shape as Claude Code's auto-mode classifier.
**[SOURCE]** Codex's own docs are now stubs: `docs/sandbox.md` and `docs/execpolicy.md` contain one line each pointing at `developers.openai.com`, which returned **HTTP 403** to my fetcher (WAF). Codex's sandbox description below therefore rests on source code and security disclosures, not vendor prose.

**Cursor.**
**[SOURCE]** "Crashes, timeouts, and non-zero exit codes other than 2 **fail open by default**: Cursor logs the failure and allows the action through. Set `failClosed: true` ... This is recommended for security-critical `beforeMCPExecution` hooks." But: "Permission hooks **block on invalid JSON or an invalid response even when this is `false`**." Exit code 2 blocks. `preToolUse` is a generic pre-execution hook firing for all tools; `beforeShellExecution`/`beforeMCPExecution`/`beforeReadFile` return `permission: allow | deny | ask`. Hooks may be prompt-based: an LLM is asked "Does this command look safe to execute?" and returns `{ok, reason}`.
**[SOURCE]** Cloud agents: "sometimes begin in a read-only environment for early exploratory turns. **Hooks do not run during those turns.**" `sessionStart` is "deferred ... a cloud `sessionStart` would fire too late (after the first write)". `beforeMCPExecution` is deferred for the same reason.

**MCP.**
**[SOURCE]** The tools spec: "Implementations are free to expose tools through any interface pattern that suits their needs - **the protocol itself does not mandate any specific user interaction model**." The strongest sentence is a **SHOULD**: "For trust & safety and security, there **SHOULD** always be a human in the loop with the ability to deny tool invocations. Applications **SHOULD**: Provide UI that makes clear which tools are being exposed ... Insert clear visual indicators when tools are invoked ... Present confirmation prompts". I grepped the whole file: the words `approval`, `permission`, and `consent` **do not appear**; there is no protocol message whose semantics are "the user approved this call".
**[SOURCE]** Elicitation is *server-initiated data collection*, not approval: "the protocol itself does not mandate any specific user interaction model"; servers **MUST NOT** use it "to request sensitive information". The client-side obligations are all SHOULD (show which server is asking, let users review and modify, provide decline/cancel). The response vocabulary is `accept | decline | cancel` on a request for *information*.

**OpenAI Agents SDK.**
**[SOURCE]** "**Parallel execution (default, `run_in_parallel=True`)**: The guardrail runs concurrently with the agent ... however, if the guardrail's tripwire is triggered, the agent **may have already consumed tokens and executed tools** before being cancelled." Blocking mode (`run_in_parallel=False`) is opt-in. "**Input guardrails run only for the first agent in the chain.**" "Tool guardrails run on every guarded function-tool invocation ... with input guardrails **before execution** and output guardrails **after execution**."
**[CODE]** `InputGuardrail.run_in_parallel: bool = True`. `ToolGuardrailFunctionOutput.behavior` defaults to `AllowBehavior(type="allow")`; the other options are `reject_content` (reject but continue with a message to the model) and `raise_exception`.

**OpenHands.**
**[SOURCE]** Two mechanisms: a **confirmation policy** (`AlwaysConfirm()`, `NeverConfirm()`, `ConfirmRisky()`) and a **security analyzer** that "analyze[s] each action and assign[s] a security risk level: LOW / MEDIUM / HIGH / **UNKNOWN** - Risk level could not be determined". The default analyzer is `LLMSecurityAnalyzer`: "It leverages **the LLM's understanding of action context** to provide lightweight security analysis. **The LLM can annotate actions with security risk levels during generation**, which the analyzer then uses to make security decisions." Confirmation is surfaced as a conversation state: the application loop must notice `WAITING_FOR_CONFIRMATION`, call `ConversationState.get_unmatched_actions(...)`, and then `reject_pending_actions(...)` or continue.

**GitHub Copilot coding agent.**
**[SOURCE]** "By default, Copilot's access to the internet is limited by a firewall." Blocked requests do not silently fail: "a warning is added to the pull request body (for new pull requests) or to a comment", naming address and command.
**[SOURCE]** GitHub documents the gate's holes itself: "**Only applies to processes started by the agent**: The firewall only applies to processes started by the agent via its Bash tool. It does not apply directly to MCP server processes or processes started in configured Copilot setup steps." / "**Only applies within the GitHub Actions appliance** ... does not apply to processes running outside of this environment." / "**Bypass potential**: Sophisticated attacks may bypass the firewall ... These limitations mean that the firewall provides protection for common scenarios, but **should not be considered a comprehensive security solution**."

**Devin.** Not reachable: no fetchable documentation of its permission/approval model was found; see "Could not verify".

### Part B - AI conventions

**AGENTS.md (the standard's own site).** "A simple, open format for guiding coding agents, used by **over 60k open-source projects**"; "**No** required fields. AGENTS.md is just standard Markdown." Nested files: "Agents automatically read the **nearest file** in the directory tree, so the closest one takes precedence"; "at time of writing the main OpenAI repo has 88 AGENTS.md files". Conflict rule: "The closest AGENTS.md to the edited file wins; **explicit user chat prompts override everything**." Stewardship: "AGENTS.md is now stewarded by the **Agentic AI Foundation under the Linux Foundation**." The ecosystem list (Codex, Jules, Cursor, Copilot, Zed, Devin, Amp, Warp, goose, Aider, ...) is published by the standard itself.

**Measured effect (the only rigorous number found).** **[SOURCE]** AGENTbench, 138 instances across 12 repositories with developer-written context files: "developer-provided files only marginally improve performance ... (**an increase of 4% on average**), while LLM-generated context files have a small negative effect ... (**a decrease of 3% on average**)" and "context files lead to increased exploration, testing, and reasoning by coding agents, and, as a result, **increase costs by over 20%**". Behaviourally: "**coding agents tend to respect their instructions**" / "Instructions in context files are typically followed". Recommendation: omit LLM-generated context files; include "only minimal requirements".

**CLAUDE.md.** **[SOURCE]** "Claude treats them as **context, not enforced configuration**. **To block an action regardless of what Claude decides, use a PreToolUse hook instead.**" Files in the directory hierarchy above the working directory load at launch; subdirectory files "load on demand when Claude reads files in those directories". Imports ("`@path`") "still load and **enter the context window at launch**". Anthropic's own quality guidance is advisory and admits the contradiction failure: "target **under 200 lines** per CLAUDE.md file. Longer files consume more context and **reduce adherence**"; "**if two rules contradict each other, Claude may pick one arbitrarily.**" Dead-file hazard documented first-party: "**Not read**: `AGENTS.local.md`, `AGENTS.override.md`, or anything under a `.agents/` directory"; and "subagents that skip project instructions skip these files too". AGENTS.md is only read as a fallback: Claude "reads AGENTS.md only when you have **no** CLAUDE.md in your working directory or above it".

**Cursor rules.** **[SOURCE]** Four types: Project Rules (`.cursor/rules`, `.mdc`), User Rules, Team Rules, and AGENTS.md. "Project rules **must** use the `.mdc` extension. A plain `.md` file in `.cursor/rules` **is ignored by the rules system** because it has no frontmatter to specify `description`, `globs`, and `alwaysApply`." Activation is decided by the `alwaysApply`/`description`/`globs` matrix, including "**Apply Intelligently** - When Agent decides it's relevant based on description".

**GitHub Copilot.** **[SOURCE]** Three kinds: repository-wide `.github/copilot-instructions.md`; path-specific "`NAME.instructions.md` files within or below `.github/instructions`"; and "Agent instructions" via AGENTS.md, where "**the nearest AGENTS.md file in the directory tree will take precedence**"; "you can use a single `CLAUDE.md` or `GEMINI.md` file stored in the root of the repository". Precedence: "Personal instructions take the highest priority. Repository instructions come next, and then organization instructions are prioritized last. **However, all sets of relevant instructions are provided to Copilot.**" On contradiction, the guidance is human discipline: "Whenever possible, **avoid** providing conflicting sets of instructions."

**Kiro steering (AWS).** **[SOURCE]** Markdown under `.kiro/steering/` (workspace), `~/.kiro/steering/` (global), or cloud; "In case of conflicting instructions between global and workspace steering, Kiro will **prioritize the workspace** steering instructions." Foundation files `product.md`, `tech.md`, `structure.md` are "included in every interaction by default". Inclusion modes via YAML front matter: `inclusion: always` (default) or `inclusion: fileMatch` + `fileMatchPattern`; the docs also list `manual`. "AGENTS.md files ... **do not support inclusion modes and are always included**", and are discovered in subdirectories.

**Spec-driven development (GitHub Spec Kit).** **[SOURCE]** "Constitution once per project; specify -> plan -> tasks -> implement -> converge per feature." "Repeat **implement -> converge** until convergence reports **Converged**. Add clarification, checklists, and consistency analysis when you need extra quality gates."

**Zed.** Not verified; see "Could not verify".

## What I read in code

- **[CODE] Claude Code hooks, exit-code table.** The gate semantics are a table, not a sentence: `PreToolUse` "Can block? **Yes**"; `PermissionRequest` "Can block? **No** - Exit code 2 isn't honored for this event". The lifetime of a "run once" hook is defined so that failure does not drop the hook: "A run that fails, blocks with exit code 2, or times out **leaves the hook in place**".
- **[CODE] Claude Code permission modes.** The load-bearing control is the **deny rule**, not the mode: "Deny rules block in every mode, including `bypassPermissions`", while "Allow rules have no effect in `bypassPermissions`". And "Writes to protected paths are never auto-approved except in `bypassPermissions` mode" - i.e. the strictest mode still has to be told no by a rule, not by a policy.
- **[CODE] Codex `AskForApproval` and `GranularApprovalConfig`** (quoted above). This is the cleanest fail-closed gate semantics of any system surveyed: a category set to `false` is **auto-rejected**, and `Never` "never escalates" - there is no window in which an unanswerable prompt becomes an allow.
- **[CODE] Codex filesystem policy precedence** (quoted above). Deny > write > read as an explicit ordering in the type's doc comment, not an implementation accident.
- **[CODE] `codex-rs/core/src/safety.rs`** carries the patch-specific rejection reasons, i.e. the write path is checked against the configured filesystem policy before the patch is applied. This is the *shape* of the fix for the class of bug described in Overpatch.
- **[CODE] Agents SDK defaults.** `run_in_parallel: bool = True` on `InputGuardrail`; `behavior` defaulting to `AllowBehavior(type="allow")` on `ToolGuardrailFunctionOutput`. Both strongest-sounding controls default to *not interfering*.
- **[CODE] MCP tool-call spec contains no approval verb.** Negative result from reading `server/tools.mdx` in full: `approval`, `permission`, `consent` absent; the human-in-the-loop clause is SHOULD-level.
- **[CODE] OpenHands risk levels include `UNKNOWN`** ("Risk level could not be determined") with no documented fallback behaviour in the guide I read, and the only shipped analyzer derives the level **from the model's own annotation during generation**.

### When the gate cannot evaluate: fail open / fail closed / ask

| System | Control | Cannot evaluate (timeout / crash / malformed) | Verdict |
|---|---|---|---|
| Claude Code | `PreToolUse` command/`http`/`mcp_tool` hook | continues through normal permission flow | **fail open** (documented) |
| Claude Code | Agent SDK callback hook | blocks the tool call | **fail closed** |
| Claude Code | hook stdout unparseable / schema-invalid | "non-blocking error: the action proceeds" | **fail open** |
| Claude Code | deny rule vs hook `allow` | deny still evaluated; exit 2 unoverridable by JSON | **deny wins** |
| Codex | `GranularApprovalConfig` field `false` | auto-rejected, not shown | **fail closed** |
| Codex | approval =`Never` | failures returned to model, never escalated | **no ask path exists** |
| Codex | filesystem policy | deny > write > read precedence | **deny wins** |
| Cursor | permission hooks | invalid JSON/schema **blocks**; crash/timeout/non-zero-exit **allows** unless `failClosed: true` | **mixed; fail open by default** |
| OpenHands | `ConfirmRisky` + analyzer | risk `UNKNOWN` exists; behaviour on UNKNOWN not stated in the guide I read | **undocumented** |
| Agents SDK | input guardrail | default is parallel, so the answer arrives after the model may already have acted | **fail open in practice** |
| Copilot coding agent | network firewall | blocked request allowed to be *noticed after the fact* on the PR body; agent-side "bypass potential" acknowledged | **partially structural** |
| MCP | anything | no protocol-level approval exists to fail | **not applicable** |

**[OPINION]** The two vendors who got the *default* right are Codex (a `false` granular category is auto-rejected) and Claude Code's deny/exit-2 channel (unoverridable by the same channel). Cursor's model is the clearest counter-example: it makes fail-closed an **opt-in per hook** ("`failClosed: true` ... recommended for security-critical hooks"), which means every hook written before someone reads that line is a gate that silently degrades to a log line.

## What is transferable to a harness

**A1. The gate belongs at the boundary the action cannot route around, and the enforcement decision must live outside the thing being enforced.** [OPINION] For the three verticals in this project's scope, that boundary is: the process/filesystem/network sandbox for shell-and-file work, and the *credential/quota* boundary for trading. A gate implemented as "the tool wrapper checks the arguments" is exactly the Overpatch/apply_patch shape: the wrapper was the thing that computed its own permission from the input it was handed.
[SOURCE] Accomplish's own conclusion, which is also the only position that survives all six bypasses above: "The thing doing the enforcement was sitting inside the thing being enforced ... nothing that decides what is allowed is running in there with it."

**A2. Separate the *pre-execution policy* from the *approval prompt*, and give the policy a fail-closed rule for "cannot decide".** This is what this project's `src/core/gate-limit.ts` and `gate-conformance.ts` already specify (a limit whose argument is absent/non-numeric/non-finite is a **block**; an unmappable action is a **block**). Codex's `GranularApprovalConfig` is the shipping precedent: a category set to `false` is auto-rejected rather than queued. Cursor's opt-in `failClosed` and Claude Code's fail-open hook timeout are the negative examples.

**A3. Two gate semantics are needed, and the shipping products show why.** [SOURCE] `ConfirmRisky` vs `AlwaysConfirm` (OpenHands), `UnlessTrusted` vs `OnRequest` vs `Never` (Codex), `default`/`acceptEdits`/`dontAsk`/`bypassPermissions` (Claude Code). [INFERENCE] These map cleanly onto the two semantics already in `src/core`: a **limit** gate (SEC 15c3-5 style threshold, denies in-scope actions) and a **conformance** gate (NIST SP 800-115 style rules of engagement, allows everything inside pre-established scope). A framework with only one forces the other vertical to bypass it - which is precisely how it was written in this repo, and the survey supports it.

**A4. Deny must be a different channel from allow, and unoverridable by the allow channel.** [CODE] Claude Code: "Deny rules block in every mode, including `bypassPermissions`"; "Exit 2's block is the one outcome JSON can't override"; "Deny and ask rules are still evaluated regardless of what the hook returns". Codex: an explicit deny/write/read conflict ordering. [OPINION] A harness whose gate can be turned off by the same document that configures it (a hook, a settings file the agent can write) has no gate. Note the harness must also decide *who may edit the gate*: Codex's Heapjack used a native tool that "exposes a tool for editing the global `~/.codex/config.toml`".

**A5. Register the gate's *coverage*, not just its existence.** Every bypass found would have been caught by asking "which execution paths reach the filesystem/network without passing this check?" [OPINION] Concretely for this project: the gate record should name the set of entry points it covers (model tool call, harness-internal subprocess, hook-spawned subprocess, MCP server process, setup step), because the four published escapes are all of the form "the gate covered one of those five".

**A6. A hook is a subprocess with a timeout; treat every one of its failure modes explicitly.** Claude Code's rule ("a timed-out command hook doesn't block the tool call ... don't count on a stalled hook to act as a gate") is the general law. [OPINION] If the harness's entry gate is a hook/plugin, it must be given: a declared fail-closed flag, a declared timeout, a declared coverage matcher, and a startup self-test that proves it fires for each covered entry point.

**B1. Use AGENTS.md as the *filename and discovery* layer; do not adopt any vendor's front-matter schema as the harness's format.** [SOURCE] AGENTS.md has genuinely converged on the filename, the "nearest file wins" resolution, and "plain Markdown, no required fields" - and it is now read by Claude Code (as a fallback), Cursor, Copilot, Kiro and Codex. The *formats* around it have not converged: Cursor `.mdc` + `alwaysApply`/`globs`/`description`, Copilot `.github/instructions/NAME.instructions.md` + `applyTo`, Kiro `inclusion: always|fileMatch|manual`, Claude `.claude/rules/`. [INFERENCE] These are four incompatible encodings of the same idea (always / by-glob / by-description / by-hand).

**B2. Write down the conventions you will actually load, and keep them minimal - the only benchmark says so.** [SOURCE] AGENTbench: developer-written context files +4%, LLM-generated -3%, cost +20%+, agents "tend to respect their instructions". Author recommendation: "include only minimal requirements". Anthropic states the same from the other side: "target under 200 lines ... longer files consume more context and reduce adherence".

**B3. Detection of dead and contradicting rules needs to be a harness feature, because no shipping product has it.** [SOURCE] Every product surveyed answers "what if two conventions conflict?" with prose: AGENTS.md "the closest wins; explicit user chat prompts override everything"; Copilot "avoid providing conflicting sets"; Kiro "workspace beats global"; Anthropic "Claude may pick one arbitrarily" and points you at a periodic manual review. [SOURCE] The only *checking* mechanism found is a reporting feature, not a gate: Claude Code's hook lifecycle includes a `InstructionsLoaded` event, and the memory page states "To confirm the file loaded, run `/context` in a session and check the list under **Memory files**". [OPINION] This is the cheapest high-value thing this harness can do better than every product surveyed: make the convention loader emit which files it loaded, which rules it classified as always/globs/description/manual, and which files in the conventions directory were **never** loaded. A rule that is never loaded is the same defect this project already named - "a helper that exists but is never called is not enforcement" - applied to prose.

**B4. Conventions are advisory by construction; if a convention must hold, it must be promoted to a gate.** [SOURCE] Anthropic says this outright: "Claude treats them as **context, not enforced configuration**. To block an action regardless of what Claude decides, use a PreToolUse hook instead." [INFERENCE] So a harness convention file should distinguish *stated* conventions from *enforced* ones, and every enforced one should name the gate that enforces it. The nearest thing to checking output against a convention found anywhere is Spec Kit's `/speckit-converge` loop ("Repeat implement -> converge until convergence reports Converged") - and the checker there is the agent itself, i.e. advisory with a stronger appearance of rigour.

## Caveats / Not Found

1. **Vendor-adjacent security research.** The Accomplish writeups are the strongest single source on bypass mechanics and they end with a product pitch ("That's why Accomplish runs the whole agent inside a VM"). **This is vendor marketing attached to a credible disclosure.** I cite the technical claims because they are specific (argv captures, version numbers, process ancestry) and independently corroborated, but the *conclusion* - "put everything in a VM, trust nothing in the guest, root included" - is the vendor's sales position, not a measured result. Rank the writeups as named-engineer post-mortem with a disclosed conflict of interest.
2. **The `InstructionsLoaded` hook is weakly verified here.** I observed the event name in the hook-lifecycle list of the hooks reference, but the page was truncated at my fetch limit (100,000 chars for the `.md` variant), so I did not read that event's own section. Do not build on it without re-reading the docs.
3. **Dates in this document are as printed by the sources.** Several are dated 2026 (e.g. Beltdown2's proof reads `2026-07-27`); I recorded them as shown rather than normalising.
4. **Cursor's `preToolUse` output schema shows `permission: allow | deny` while `beforeShellExecution`/`beforeMCPExecution` show `allow | deny | ask`.** I read both shapes in the same page and did not resolve whether `ask` is genuinely unavailable on `preToolUse` or is a documentation omission. This matters if the harness wants "ask" semantics on a generic hook.
5. **No product surveyed checks agent output against its conventions at the host level.** The nearest are Anthropic's "use a PreToolUse hook instead" advice and Spec Kit's agent-run convergence loop. If the parent's design assumes a precedent for automated convention conformance, there is not one.
6. **The strongest evidence for Must-answer 1 is a named pair, not a single item:** `CVE-2026-55607` (Claude Code, worktree + `core.fsmonitor` -> unsandboxed execution; GHSA-7835-87q9-rgvv; fixed 2.1.163) and `CVE-2025-59532` (Codex, model-generated `cwd` as writable root; fixed 0.39.0). If a single citation is needed, use CVE-2026-55607: it is a sandbox escape in the strictest mode, with a CVE record, a GHSA, a credited external reporter and a version boundary.

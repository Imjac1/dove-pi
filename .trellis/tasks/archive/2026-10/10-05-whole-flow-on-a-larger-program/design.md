## 为什么它现在做不到（**实测** ✓✓）

规格 §2 自己写着：*"**most of them are not field-runnable**. … Their assertions are written against **scripted** events, so pointing a real model at them **does not test what they assert**."* ✓✓

→ **所以新增场景的关键不是"多一个文件"，而是"断言建在真实模型能产生的观察上"** ✓✓：§4 的读数里**有一项正是为此存在的** ✓ —— **"tools the model actually called, with counts"** ✓✓（脚本事件没有"模型自己选了什么工具" ✓✓）。**再加上 `stopReasons` 的列表** ✓（不是长度 ✓）与 `terminalConsistency` ✓✓。

## 对照跑（**C 能成立的前提** ✓✓）

```
① 控制跑：项目 + 场景，agent 不做任何改动
② 流程跑：同一项目 + 同一场景，走完 1→5
③ 归因：只把 ①→② 的**差值**算作 harness 的行为
```

**为什么必须有** ✓✓：规格 §4 的标题就是 *"Reading Format and **Its Comparison**"* ✓✓ —— 没有它，**项目自身的既有失败会被误算成 harness 的** ✗✓，而 C（在已有大项目上）**天生就有既有失败** ✗。

## 契约（逐条可测 ✓）

1. **每个新场景声明 `requires: "a real provider; …"`** ✓✓，且**断言只读 §4 的字段** ✓（不得读脚本事件的字段 ✗）。
2. **每一轮的读数按 §4 记录** ✓，**含 `tokens`** ✓ 与 **模型实际调用的工具及次数** ✓✓。
3. **控制跑先于流程跑** ✓✓，且**两次的差异被显式写出来** ✓（不是"看起来差不多" ✓）。
4. **项目自己的测试是判分** ✓；harness 的读数**不替代**它 ✗✓。
5. **原始证据（`--output`）在仓外** ✓✗，且**没有任何一次运行把它提交进仓** ✗。

## 项目的四条标准（推导自 C 的代价 ✓，不是偏好 ✓）

① 有自己的测试套件 ✓（判分来源 ✓）② 有真实依赖 ✓ ③ 比 `yocto-queue`（~300 行 ✓）大一档 ✓ ④ 能整体克隆、无需凭据 ✓。**选 Python** ✓✓（跨生态 ✓ = 仪器会遇到没见过的形状 ✓；**本仓已有 141 个 `unittest` 通过** ✓✓，证明这条路不是未知 ✓；无编译 ✓ → 不浪费 15 分钟预算 ✓）。

## 取舍与回退

- **取舍** ✓：跨生态换诊断价值 ✓，代价是**部分失败可能出在跨生态支持本身** ✗✓ —— 由**对照跑**分开 ✓✓。
- **风险** ✗：新场景**断言写得像脚本事件** → 那就重复了现有的问题 ✓ → 由契约 1 压住 ✓；**控制跑与流程跑不同参** → 差异不可归因 ✗ → 由契约 3 要求**显式写出差异** ✓。
- **回退** ✓：新场景是**新增文件** ✓、不动既有 8 个 ✓；`--output` 在仓外 ✓ → 回退面小 ✓。

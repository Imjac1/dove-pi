# Dove Pi 审计记录（2026-08-27）

## 范围与结论

本次只做代码、运行配置和已安装扩展的证据审计，不修改产品代码。仓库没有 `models.json`；该文件属于 Pi 用户级配置目录（通常为 `PI_CODING_AGENT_DIR/models.json`，默认 `~/.pi/agent/models.json`）。Dove 目前读取 Pi runtime 提供的模型/上下文信息，但没有独立的模型路由层。

## 已确认的问题

### P0：用户级模型配置包含明文凭据风险

本机 Pi 用户配置中的 `models.json` 存在明文 API key 字段。该文件不属于 Dove 仓库，但一旦被备份、同步或误提交就会泄露凭据。建议立即轮换该 key，并改用环境变量或 Pi 的凭据存储；Dove 的 doctor/日志不应读取或打印 secret 内容。

### P0：Dove 与 hashline-edit 存在编辑权威冲突

- `src/pi-adapter/tool-profile.ts` 的 `CORE_TOOL_NAMES` 仍包含 `read`、`edit`、`grep`。
- `src/pi-adapter/extension.ts` 在 `session_start` 和 `before_agent_start` 会调用 `setActiveTools()`。
- 已安装的 `pi-hashline-edit-pro` 在 `session_start` 执行 `setActiveTools(active.filter(t => t !== "edit"))`，README 明确说它替换内置 `read`/`grep` 并禁用内置 `edit`。
- 当前 `max` profile 同时包含 hashline-edit，且 `dove-pi extensions doctor max` 返回 `ok: true`、无 issues。

因此 doctor 存在漏报，Dove 可能重新暴露内置 `edit`，模型同时看到两套编辑路径，且 hashline 的锚点安全约束可能被绕开。应选择唯一编辑权威：检测到 hashline 时排除内置 `edit`（必要时也排除内置 `read`/`grep`），或把 hashline 从默认 profile 移出，直到完成兼容适配。

### P0：`/mode ultra` 与 Pi thinking level 语义脱节

- `ModeController` 只维护 Dove 的 `fast|standard|ultra`。
- `setMode()` 只记录 Dove mode、刷新状态和提示，没有调用 Pi 的 `setThinkingLevel()`。
- 当前状态栏的 `thinkingMax` 只是颜色主题；不能证明模型实际以最高 thinking level 请求。
- Pi 本身支持 `getThinkingLevel()`/`setThinkingLevel()`，而用户级 `models.json` 的 `thinkingLevelMap` 决定 provider 可接受的实际值。

这会让用户把“Ultra”理解成模型推理等级已提升，但实际可能只改变上下文检索、工具和执行策略。需要明确协议：要么 Ultra 显示并同步“最高可用 thinking level”，要么明确 Dove mode 与 Pi thinking 是两个独立旋钮，并在 `/status full` 同时展示二者。

### P1：默认全量安装与启动全量混在一起，造成冷启动风险

安装器默认 profile 为 `max`，并将 MCP、网页、原生浏览器、lens、background tasks、hashline 等包写入 Pi settings。即使 Dove `auto` 没有把这些工具 schema 暴露给模型，扩展本身仍会加载并执行各自的 `session_start` 初始化；其中 lens 明确包含扫描/预热阶段，其他扩展也可能探测外部工具或服务。

更合适的分层是“依赖全量安装、运行时按需激活”：保留全量包可用，但默认只启动轻量/安全扩展；重型能力按意图、命令或项目阶段显式激活，并提供冷启动耗时和失败降级诊断。这样不违背“默认都安装”，同时避免新目录首次启动卡顿。

### P1：`auto` 工具集合只增不减的长期成本

当前实现为了保持 prompt cache 前缀稳定，在会话内单调累加意图工具。它解决了每轮重算导致的缓存抖动，但长会话一旦触发 browser/LSP/MCP/background，工具 schema 会一直保留到会话结束，最终接近 `full`。

建议把工具生命周期改成“阶段固定、显式重置”：会话启动建立 core 集合；首次进入某种任务阶段时一次性加入该阶段工具；`/dove-tools reset`、`/new` 或阶段切换时允许重新建立集合。更长期的方案是稳定的 tool broker/search 工具，避免反复修改真实工具集合。

### P1：doctor 不能解释 provider/cache 路由

`src/cli.ts doctor` 和项目 doctor 当前主要报告 Node、PowerShell、Trellis 与任务状态，不报告实际 Pi provider/model、API 类型、代理/路由、缓存能力或 cache optimizer 诊断。这正是用户会误以为 Dove 仓库应该拥有 `models.json` 的原因。

建议增加只读 runtime 诊断（例如 `dove-pi doctor --runtime` 或 Pi `/status full`）：显示 provider/model、配置来源、是否为 OpenRouter/第三方代理、是否支持 session affinity/prompt cache，以及缓存统计的口径；绝不打印凭据。固定 OpenRouter 上游仍应由 Pi 用户配置负责，Dove 只诊断和提示，不复制或自动改写模型配置。

### P1：缺少主动 compaction 的可见边界

当前 Ultra 已按实际 `contextWindow` 为 Dove 项目上下文计算预算，但没有在整体会话接近上限时给出明确提示或触发 Pi 原生 compaction。审计过的大型会话输入曾增长到约 172K token，未观察到明显 compaction 事件。

后续应在安全边界检测 Pi context usage：先提示，再允许用户 `/compact`；若自动化，必须调用 Pi 原生 compaction，只在工具链空闲时触发，避免 Dove 再造一套历史摘要系统。

### P2：工具结果压缩仍有媒体语义风险

`compactToolResultContent()` 超过文本预算时只返回一个 text block。若原始结果同时包含 image block，会把图片从模型侧结果中丢掉；原文虽然放入 details，但模型并不一定能读取 details。应只压缩 text、保留 image，并为原始文本使用可追踪 artifact/reference。

### P2：Provider projection 仍把所有文档读入内存

`TrellisProvider.getContext()` 每次刷新会读取发现到的任务/spec/workflow/memory 文档全文，再由 compiler 截断。250ms 缓存只解决同一请求内重复扫描，不解决大型 Trellis 项目的首次 I/O 和内存峰值。长期应改为索引优先、按查询读取相关片段，保留 revision/mtime 失效机制。

## 当前边界与非问题

- Provider 选择顺序（显式 `.dove/project.json` > Trellis 发现 > lightweight）是有意设计，不是冲突；`lightweight` 可以作为显式降级模式。
- Trellis 250ms cache 适合作为请求内去重，不应扩展成跨长时间的隐藏缓存。
- OpenRouter 多上游导致 cache 命中下降属于路由层问题，不应在 Dove 核心复制 `models.json` 或自动替用户改 provider。
- 当前活动 Trellis 任务仍是 `08-26-personal-agent-os`，`08-27-dove-interop-layer` 处于 planning 且未启动；本次审计材料写入后者，避免误把规划当成已批准实现。

## 推荐推进顺序

1. 修复 hashline/Dove 编辑权威冲突，并让 doctor 能报出实际冲突（P0）。
2. 定义并实现 Dove mode 与 Pi thinking 的明确契约，状态栏同时展示二者（P0）。
3. 将“全量安装”与“默认启用”拆开，重型扩展延迟激活，加入启动耗时/降级诊断（P1）。
4. 重新设计 `auto` 工具集合生命周期，控制长会话 schema 膨胀（P1）。
5. 增加 runtime/provider/cache doctor，但保持 Pi 用户配置为唯一模型路由权威（P1）。
6. 增加 context usage 提示与 Pi 原生 compaction 边界；随后处理图片保留和 provider 索引化（P1/P2）。
7. 在上述稳定后，再推进 MCP/CLI/RPC Capability Protocol 和外部 host adapter（P2）。

## 待用户确认的一个产品决策

推荐采用：**安装器仍全量安装，但默认只启用轻量核心；重型扩展按需激活；`/mode ultra` 不偷偷改变 Pi thinking，而是显式显示并提供同步选项。**

取舍是首次使用更快、语义更清楚，但需要增加一层扩展激活状态和 `/status` 展示；如果用户更重视开箱即用的全部能力，也可以选择“全量安装且全量启用”，但应接受更长冷启动和更高 schema/context 成本。

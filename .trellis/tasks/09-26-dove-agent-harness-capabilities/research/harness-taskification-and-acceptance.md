# Research: Taskification, PRD planning, and acceptance criteria in agent harnesses and spec-driven-development tools

- **Query:** How do agent harnesses and spec-driven development tools turn a request into tracked,
  planned, checkable work? Sub-questions: taskification (unit / states / where state lives / concurrent
  access), PRD planning (artifacts, approvers, whether a phase is literally gated), and acceptance
  criteria (how "done" is expressed and what checks it).
- **Scope:** the 9 external projects named in the brief (GitHub Spec Kit, BMAD-METHOD, Amazon Kiro,
  agent-os, OpenSpec, aider, SWE-agent, Devin, OpenHands) plus the two in-repo implementations
  (`.trellis/`, `src/core/`). Priority given to code and to files that read/write state.
- **Date:** 2026-09-26. Repo metadata read from `api.github.com/repos/<owner>/<name>` on this date.
- **Method note:** GitHub's unauthenticated REST API (60 req/h) was exhausted mid-research, and
  `raw.githubusercontent.com` / `cdn.jsdelivr.net` returned intermittent transport errors.
  Where a file could not be fetched, it is recorded under **Could not verify** rather than reconstructed
  from memory.

## What the sources state

### GitHub Spec Kit - three artifacts, a shell gate, a human checklist gate, a read-only analyzer

**(a) Stated, official repo docs/templates.** Spec Kit defines a per-feature directory of artifacts
generated by slash commands: `spec.md` (requirements), `plan.md` (technical plan),
`tasks.md` (implementation tasks), plus optional `research.md`, `data-model.md`,
`contracts/`, `quickstart.md`. Source: `templates/spec-template.md` and
`templates/tasks-template.md`, fetched from
https://raw.githubusercontent.com/github/spec-kit/main/templates/spec-template.md and
https://raw.githubusercontent.com/github/spec-kit/main/templates/tasks-template.md (repo github/spec-kit,
MIT, last commit 2026-09-25).

The spec template carries mandatory sections with stable IDs: **Functional Requirements FR-001, FR-002 ...**
and **Success Criteria SC-001 ...** described as "technology-agnostic and measurable", plus per-user-story
**Acceptance Scenarios** in Given/When/Then form and an **Independent Test** line. The tasks template
expresses work as Markdown checkboxes `- [ ] T001 ...` grouped by phase and user story, with
`[P]` parallelism markers and the rule "Tasks MUST be organized by user story so each story can be
... Tested independently".

The `/implement` command template declares a prerequisite script in YAML front-matter:
`scripts: sh: scripts/bash/check-prerequisites.sh --json --require-tasks --include-tasks`
(`templates/commands/implement.md`, fetched from
https://raw.githubusercontent.com/github/spec-kit/main/templates/commands/implement.md). `/analyze`
and `/converge` add `--require-spec --require-tasks`.

**(a2) The checklist is explicitly a human review gate.** `checklist-template.md` states:
"**Review Ownership**: This checklist is a reviewer-owned requirements-quality review artifact. Mark an
item [x] only when the reviewer determines the requirements-quality criterion is satisfied." and
"`/implement` reads checklist checkbox state as a gate and must not modify markers" (fetched
https://raw.githubusercontent.com/github/spec-kit/main/templates/checklist-template.md).

### OpenSpec - a deterministic validator with a non-zero exit code

**(a) Stated.** OpenSpec's model is *specs* grouped by capability plus *changes* (proposals) made of delta
specs and task lists under `openspec/changes/`. Validation is a first-class CLI command.

**(b) Observed in code.** `src/core/validation/validator.ts` composes Zod schemas with rule passes:
delta specs must contain at least one delta; ADDED/MODIFIED requirements must each have at least one
`#### Scenario:` block; the SHALL/MUST keyword check is "guidance unless strict mode is enabled";
REMOVED/RENAMED have their own shape rules (https://raw.githubusercontent.com/Fission-AI/OpenSpec/main/src/core/validation/validator.ts,
repo Fission-AI/OpenSpec, MIT, last commit 2026-09-25). `constants.ts` fixes messages and
thresholds: `REQUIREMENT_NO_SHALL: 'Requirement must contain SHALL or MUST keyword'`,
`REQUIREMENT_NO_SCENARIOS: 'Requirement must have at least one scenario'`,
`MIN_PURPOSE_LENGTH = 50`, `MAX_REQUIREMENT_TEXT_LENGTH = 500` (fetched
https://raw.githubusercontent.com/Fission-AI/OpenSpec/main/src/core/validation/constants.ts).

The CLI turns these into CI semantics: `src/commands/validate.ts` sets
`process.exitCode = report.valid ? 0 : 1` for single items and
`process.exitCode = failed > 0 ? 1 : 0` for bulk runs. `openspec validate --archived` runs a
separate pass that fails an archived change with unchecked tasks, with a message built as
"N incomplete task(s) (completed/total completed)" (fetched
https://raw.githubusercontent.com/Fission-AI/OpenSpec/main/src/commands/validate.ts).

### Trellis (in-repo) - task JSON, per-session pointer, a manifest gate, a breadcrumb state machine

**(b) Observed.** See "What I read in code" for the enforcers; the *documented* model is in
`.trellis/workflow.md`: three phases (Plan, Execute, Finish), artifacts `prd.md` /
`design.md` / `implement.md` / `research/` / `implement.jsonl` /
`check.jsonl`, task states `planning -> in_progress -> completed`, and a per-turn
workflow-state breadcrumb that the file calls "the only per-turn channel".

### BMAD-METHOD - the process is prompt text; the only deterministic validator checks skills

**(a)/(b) Stated by the maintainers in `AGENTS.md`** (fetched
https://raw.githubusercontent.com/bmad-code-org/BMAD-METHOD/main/AGENTS.md, repo bmad-code-org/BMAD-METHOD,
last commit 2026-09-26): "Skills, workflows, tasks, and agent definitions are prompt text that an agent
reads in full on every run." and "Deterministic skill checks run via
`uv run tools/validate_skills.py --strict`". `tools/skill-validator.md` defines that
validator's scope: "Run the deterministic validator ... This checks 10 rules deterministically: SKILL-01
... TPL-01", with definitions such as "**Skill directory**: the folder containing `SKILL.md` and
all supporting files." (fetched https://raw.githubusercontent.com/bmad-code-org/BMAD-METHOD/main/tools/skill-validator.md).
The checked artifact is the *prompt packaging*, not a PRD, story, or acceptance result. BMAD's
product/PRD/epic/story/QA artifacts (the tree lists `bmad-create-prd`, `bmad-validate-prd`,
`bmad-create-story`, `bmad-dev-story`, `bmad-code-review`) are Markdown skills
the agent is instructed to follow.

### Amazon Kiro - documented per-phase approval gates; closed source

**(a) Vendor documentation (not code - Kiro is closed).** Kiro generates, per spec, three files under
`.kiro/specs/<name>/`: `requirements.md` (or `bugfix.md`),
`design.md`, `tasks.md`. The workflow is drawn as an approval gate:
`requirements.md -> {Happy?} --no--> Edit/Request changes --> requirements.md; --yes--> design.md ->
{Happy?} ... --> Implementation`. Requirements use EARS notation ("WHEN [condition] THE SYSTEM SHALL
[behavior]"), which the docs claim is "directly translatable into test cases". `Quick Spec` is
offered as the path that "runs all three phases automatically **without approval gates** between them",
implying the default Feature/Bugfix paths do gate. Sources: https://kiro.dev/docs/specs.md and
https://kiro.dev/docs/specs/feature-specs.md (Kiro docs, fetched 2026-09-26; pages self-identify via an
`llms.txt` index). Kiro also documents "Analyze Requirements" (cross-requirement
inconsistency/ambiguity analysis; "takes minutes") and "Correctness" property-based testing (IDE only)
that "automatic[ally] translat[es] natural language specifications into executable properties"
(https://kiro.dev/docs/specs/analyze-requirements.md, https://kiro.dev/docs/specs/correctness.md).

### agent-os - a plan-mode prerequisite, otherwise prompts

**(d) Opinion.** These two are execution engines, not process frameworks; they matter to the harness as

## What I read in code

### 1. Trellis taskification is a real state machine with a real gate

**The unit is a directory** `.trellis/tasks/{MM-DD-slug}/` holding `task.json`,
`prd.md`, optional `design.md`/`implement.md`/`research/`, and the
`implement.jsonl`/`check.jsonl` context manifests. Identity/state/history fields are
concrete (read from `.trellis/tasks/09-26-dove-agent-harness-capabilities/task.json`):
`id, name, title, description, status, dev_type, scope, package, priority, creator, assignee,
createdAt, completedAt, branch, base_branch, worktree_path, commit, pr_url, subtasks, children, parent,
relatedFiles, notes, meta`. States observed in code: `planning` (set by `create`),
`in_progress` (`start`), `completed` (`archive`, which also moves the
directory under `archive/{year-month}/` and deletes session pointers that name it - `.trellis/workflow.md`).

**The gate that actually refuses** is the context-manifest gate in `cmd_start`,
`.trellis/scripts/task.py:196-217`:

```python
# Context-manifest gate (#573): a seeded-but-uncurated implement/check
# manifest means every sub-agent dispatched for this task runs with zero
# spec context, and nothing downstream surfaces that to the main session.
if not getattr(args, "allow_empty_context", False):
    empty_manifests = [
        name for name in ("implement.jsonl", "check.jsonl")
        if curated_entry_count(full_path / name) == 0
    ]
    if empty_manifests:
        print(colored(f"Error: {' and '.join(empty_manifests)} ... no curated entries", Colors.RED))
        ...
        return 1
```

This is the only hard prerequisite on `task.py start`. (c) It gates *sub-agent context*, not the
existence of `prd.md` / `design.md` / `implement.md`.

**The design.md/implement.md "gate" is documentation, not enforcement.** `.trellis/workflow.md`
states "Complex tasks must have `prd.md`, `design.md`, and `implement.md`
before `task.py start`", and the Phase 1.5 completion-criteria table marks
`design.md`/`implement.md` required for complex tasks. A grep of `.trellis/scripts/**`
for `design.md|implement.md|complex` returns only two hits, both prose:
`.trellis/scripts/common/task_store.py:321` (a docstring) and
`.trellis/scripts/common/task_store.py:688` (a "Next steps" stderr line: "Complex task: add
design.md and implement.md before task.py start"). **No code path refuses `start` for a missing
design.md.** Enforcement is linguistic (the per-turn breadcrumb plus the agent's compliance).

**Two agents touching one task.** Trellis does not lock the task; it scopes the *pointer*. Identity
resolves to a per-session key and the active task is stored per session under
`.trellis/.runtime/sessions/` (`.trellis/workflow.md`). Where two concurrent windows are
ambiguous, the code deliberately degrades rather than guessing -
`.trellis/scripts/common/active_task.py:490-493`: "A ticket counts only when it is fresh ... and
only when exactly one fresh context key matches. **Two concurrent windows therefore both degrade** rather
than one inheriting the other's pointer." State files are written atomically (temp-file-then-rename):
`.trellis/scripts/common/active_task.py:564-576`, `.trellis/scripts/common/io.py`
("content goes to a temp file in the same directory"). The convergence snapshot is a single file with a
monotonic `revision`.

**The .codex hooks inject, they do not block.** `.codex/hooks.json` registers
`UserPromptSubmit -> inject-workflow-state.py` and
`SubagentStart -> inject-subagent-context.py`; nothing in the hook tree denies a tool call (grep of
`.codex/hooks/session-start.py` finds only control-flow `continue` and
`sys.exit(0)`). So on Codex the planning gate is breadcrumb text plus `task.py` exit codes.

### 2. src/core/task-convergence.ts is a real acceptance reducer - and it is unwired

This is the strongest acceptance design **in this repository**, and the brief's claim that it is referenced
only by its own tests held up. It is a pure event-sourced reducer over an `AcceptanceCriterionState[]`
(`id`, `text`, `status`, `evidenceRefs`) plus `TaskFinding[]`:

- `AcceptanceStatus = "pending" | "in_progress" | "passed" | "failed" | "waived"`;
  `TaskRunState = "working" | "verifying" | "ready_to_finish" | "checkpointed" | "blocked"`
  (lines 3-5).
- First event must be `acceptance.frozen`; the criteria text is hashed into
  `acceptanceRevision` (SHA-256), and a re-freeze with a new revision is recorded as a
  `scope_change` finding and forces `checkpointed` (lines 121-125, 292-313). This is
  genuine scope-drift detection.
- Terminal state is *computed*, never asserted: `isReady()` requires every criterion
  `passed` or `waived` **and** no open finding other than `follow_up`
  (lines 407-410); a `ready_to_finish` snapshot whose criteria are unready is rejected as invalid
  (line 199); events after `ready_to_finish` are refused (line 242).
- Anti-thrash is built in: two consecutive `task.progress_reviewed` with no meaningful progress
  force a `checkpointed` state with a `nextAction` (lines 358-368).

**(b) Observed caveat that matters for "checkable by something other than the agent's own word":**
`acceptance.passed` and `acceptance.failed` accept **optional** `evidenceRefs`
(lines 249-252), while `waived` requires exactly one `evidenceRef` (line 253). So the
reducer guarantees *consistency* (all criteria resolved, no open findings, revision pinned) but does **not**
guarantee that a "pass" is backed by an artifact. (c) The evidence binding exists but is not mandatory at
the pass transition - that is the specific hole to close if this contract is revived.

**(b) Why "unwired" is accurate.** `.trellis/scripts/common/convergence.py` is only a thin bridge to
`scripts/trellis-convergence.mts` (it shells to node+tsx), and I found no caller in the running Pi
chain in the files I read; consistent with the task PRD's own finding that every `src/core`
constructor is referenced only by its own file.

### 3. Spec Kit's "cannot start" gate is a shell script, invoked from command front-matter

`scripts/bash/check-prerequisites.sh` (fetched
https://raw.githubusercontent.com/github/spec-kit/main/scripts/bash/check-prerequisites.sh) hard-fails:

```bash
if [[ ! -f "$IMPL_PLAN" ]]; then
    echo "ERROR: plan.md not found in $FEATURE_DIR" >&2
    echo "Run $(format_speckit_command plan "$REPO_ROOT") first to create the implementation plan." >&2
    exit 1
fi
if $REQUIRE_SPEC && [[ ! -f "$FEATURE_SPEC" ]]; then ... exit 1; fi
if $REQUIRE_TASKS && [[ ! -f "$TASKS" ]]; then ... exit 1; fi
```

and `templates/commands/implement.md` binds it as the command's `scripts:` entry
(quoted above). (c) So the phase gate is real **at the shell level**, and sequencing is enforced only insofar
as the host agent runner executes the declared `scripts:` before the prompt. There is also a live
concurrency detail in this script: non-`--paths-only` runs `get_feature_paths`, which
persists `feature.json`; the comment cites "issue #3025" for the `--no-persist` opt-out -
i.e. even Spec Kit had to add a side-effect escape hatch for parallel/read-only callers.

Spec Kit's checklist gate inside `implement.md` is *human*, not machine: on unchecked items it
computes a PASS/FAIL table and then "**STOP** and ask: 'Some checklists have unchecked items. Do you want to
proceed with implementation anyway? (yes/no)'". A "yes" proceeds. The checklist is advisory-with-consent,
while `plan.md` existence is a hard precondition.

### 4. OpenSpec's validator is the only external tool here that reads requirements deterministically

`constants.ts` + `validator.ts` (URLs above) enforce, per requirement: non-empty text, a
`#### Scenario:` block, and (in `--strict`) the SHALL/MUST keyword.
`task-checkboxes.ts` flags list items that carry text but no checkbox; `task-numbering.ts`
detects ambiguous task IDs. The archived-change pass in `validate.ts` refuses an archived change
whose `tasks.md` is not fully checked, and explicitly refuses to treat an unreadable task file as
"no tasks" (`message: 'could not read task file'`). This is the closest thing in the survey to
"refuses completion without evidence", and it runs in CI via the exit code.

## What is transferable to a harness

### Must-answer 1 - Who enforces their own process in code, and who only documents it

**Enforce in code (file named):**

| Project | Enforcer file | What it actually blocks |
|---|---|---|
| Spec Kit | `scripts/bash/check-prerequisites.sh` (+ .ps1, .py), bound by `templates/commands/implement.md` `scripts:` | `/implement` (and `/analyze`, `/converge`) abort if plan.md/spec.md/tasks.md are absent |
| OpenSpec | `src/core/validation/validator.ts` + `src/commands/validate.ts` | Non-zero exit for malformed requirements; `--archived` fails unfinished task lists |
| Trellis | `.trellis/scripts/task.py` (`cmd_start`, `--allow-empty-context`) | `start` refuses while implement.jsonl/check.jsonl are seed-only |
| Trellis (unwired) | `src/core/task-convergence.ts` | Would refuse `ready_to_finish` with unmet criteria/open findings - no caller |
| BMAD | `tools/validate_skills.py` (`--strict`) | Structural validity of skill folders only - **not** the work |

**Document only:** BMAD's PRD/epic/story/QA checklists and reviewer/readiness gate files (prompt text per
`AGENTS.md`); Kiro's per-phase approval gates (vendor docs; closed source); agent-os's "must be
run in plan mode"; Devin's "define success criteria".

**(c) Inference.** Artifact-*existence* gates get coded (cheap, deterministic); artifact-*quality* gates stay
as prompts or become human consent prompts. Nothing in the survey enforces "this PRD is good" in code; the
strongest are OpenSpec's structural rules and Spec Kit's coverage report.

### Must-answer 2 - The smallest evidence-backed artifact set that keeps planning honest

Distilled from the three code-enforced systems, the minimum that survives a real checker is:

1. **A requirement list with stable IDs** (Spec Kit `FR-###`/`SC-###`; OpenSpec
   `### Requirement:` + `#### Scenario:`; Trellis `AC-[A-Z0-9][A-Z0-9_-]{0,31}`).
   Stable IDs are what make coverage map-able and scope drift hash-able (Trellis `acceptanceRevision`).
2. **Per-criterion acceptance text with at least one observable** - OpenSpec requires >=1 scenario per
   requirement; Spec Kit requires measurable `SC-###`; Trellis carries `evidenceRefs`.
3. **A task list that references the requirement IDs** - Spec Kit's `[US1]` tags and phase
   grouping; `/analyze` builds the requirement-to-task coverage table and reports zero-coverage
   requirements.
4. **A machine-readable state/status file** so "where am I" is not reconstructed from chat - Trellis
   `task.json.status` + convergence snapshot; OpenSpec `tasks.md` checkbox counts.
5. **One checker that can say no**: a script that exits non-zero, or a reducer that refuses the terminal
   transition. Without this, items 1-4 are prose.

**(d) Opinion.** Evidence binding is the weakest link everywhere I looked. Make `passed` require a
non-empty `evidenceRef` (a path, a command-output hash, a result URI) and have the checker resolve
that ref - otherwise "done" is still the agent's word. Trellis's `task-convergence.ts` is one
evidenceRef-length guard away from being the best of the set, and Trellis's own
`--allow-empty-context` escape hatch is the right precedent for making such a gate tolerable.

### Must-answer 3 - Where the boundary sits between "agent may proceed" and "human must approve"

- **Machine gates (no human):** Spec Kit `check-prerequisites.sh` (missing artifact = abort);
  OpenSpec `validate` (exit code, CI); Trellis `task.py start` manifest gate.
- **Human consent points:** Spec Kit `/implement` checklist FAIL -> "STOP and ask ... (yes/no)";
  Trellis "task-creation approval is not implementation approval" and the one-shot commit-plan confirmation
  (`.trellis/workflow.md` Phase 3.4); Kiro's per-phase "Happy? yes/no" gates (documented);
  agent-os's plan mode.
- **Human-only, no machine gate:** BMAD's reviewer/readiness gates; Devin's PR review.
- **(c) Inference.** The reliable split is mechanical -> machine, judgement -> human, and the human decision
  is always "proceed anyway?", never "is this true?". Notably, none of the tools put a human between
  *acceptance criteria* and *completion*; the human sits earlier, at plan approval.

## Caveats / Not Found

- **GitHub API exhaustion is in the record:** the unauthenticated `core` rate limit hit 0 mid-session,
  which is why several projects rest on one or two files rather than a full reading. Everything asserted
  above cites a file I actually fetched; everything else is listed under **Could not verify**.
- **Vendor documentation is labelled as such.** Kiro and Devin claims are "what the source states", never
  presented as code observation. Kiro's docs are unusually concrete (EARS, explicit gate diagram) but remain
  vendor claims about a closed product. Devin's are the thinnest - success criteria appear only as
  prompt-writing advice.
- **BMAD licence is ambiguous:** the GitHub API reports `NOASSERTION` while
  `.claude-plugin/marketplace.json` @6.12.0 states `"license": "MIT"`. Flagged, not resolved.
- **Star counts are vanity metrics** and are recorded only because the brief requires them; they do not
  correlate with enforcement. Spec Kit (138,964) and OpenSpec (70,420) both enforce; BMAD (53,474) enforces
  only its packaging; agent-os (5,450) enforces nothing.
- **The in-repo duplicate contract is the live risk.** `src/core/task-convergence.ts` is a
  better-specified acceptance model than anything found in the six external tools - and it runs nowhere.
  `.trellis/` provides taskification and a manifest gate but leaves the PRD/design gate as prompt
  text. (d) The decision the parent faces is not "which project to copy" but "which of the two in-repo worlds
  gets wired to the Pi host", and the evidence says the answer should reuse, not rebuild.
